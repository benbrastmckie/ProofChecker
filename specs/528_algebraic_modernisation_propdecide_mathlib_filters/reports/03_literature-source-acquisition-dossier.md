**2.2 Where the evidence base is thin, and what this round found when it looked.**

- **D-A's "community convention" claim.** Verified by fetching repository trees: `teorth/pfr` has `PFR/ForMathlib/…`; `UCSCFormalMethods/LeanLTL` has `LeanLTL/ForMathlib.lean`; `leanprover-community/sphere-eversion` uses `SphereEversion/ToMathlib/…`; `ImperialCollegeLondon/FLT` uses `FLT/Mathlib/…` (mirroring Mathlib's own directory tree beneath it). The convention exists and is the dominant one, but it has three spellings. `ForMathlib/` is the right choice; plan v2 should cite these four trees rather than "the community convention". The Mathlib style guide itself says nothing about downstream `ForMathlib` files (fetched `contribute/style.html`; confirmed absent).
- **D-B's form.** `Data/SetLike/Basic.lean:33-74` is Mathlib's prescriptive template for a bundled subobject: a `structure` with a `carrier`, a `SetLike` instance, `PartialOrder := .ofSetLike`, an `@[ext]` lemma, and a `copy` constructor "to fix definitional equalities". `Order/Ideal.lean:114` follows it (`instance : PartialOrder (Ideal P) := .ofSetLike (Ideal P) P`). `PrimeSpectrum` (`RingTheory/Spectrum/Prime/Defs.lean:28-36`) is likewise a `structure` and supplies `equivSubtype : PrimeSpectrum R ≃o {I : Ideal R // I.IsPrime}` (line 69) as a *bridge to* the subtype, not as the definition. Report 02 §4.3 chose the `abbrev` subtype as "lighter"; that is defensible for a project-local type but is the one place where a Mathlib reviewer would predictably push back, and it is the most likely reason the bundling half of Appendix A would be reshaped on upstreaming. **This is a Mathlib-source finding; no book adjudicates it.** It does not change (c) and does not block Phase 5; it is worth a one-line note in the plan's D-B rationale so the implementer knows the trade-off was seen.
- **D-C's "what a PR must contain".** The binding text is `templates/contribute/pr-review.md` (35.5 KB) in the leanprover-community website repo, plus reviewer practice. Neither is in any corpus. Report 02 §9's contributability claim was re-verified this round: upstream master `Order/PFilter.lean` still has zero occurrences of `IsProper`/`IsMaximal`/`IsPrime`; `Order/PrimeSeparator.lean:124-126` still carries the commented `TODO: Define prime filters in Mathlib … := by sorry`. Upstream last-commit dates: `PFilter.lean` 2026-06-08, `PrimeIdeal.lean` 2025-12-29, `PrimeSeparator.lean` 2026-08-24 — the last is after the pin, so Phase 5's optional E3 corollary should diff the upstream file before assuming the TODO's exact statement.
- **The generality question (prime filter on a distributive lattice vs ultrafilter on a Boolean algebra).** Plan v2 states the mathematics correctly. The textbook anchor for it is Davey & Priestley Ch. 10 ("Prime and maximal ideals") and Ch. 11 — not owned — or, owned but OCR-degraded, CZ Part III Corollary 7.42 / Theorem 8.14. Mathlib's `PrimeIdeal.lean:133` (`IsMaximal.isPrime`, on a distributive lattice) and `:174` (`IsPrime.isMaximal`, Boolean) already encode it; the books would supply a citation, not a fact.

**2.3 Fact the plan can lean on, not previously stated in any artifact.** The pinned Mathlib has **no Stone representation theorem for Boolean algebras and no Priestley duality**: `Order/Birkhoff.lean:40` explicitly scopes itself to "the object part of *finite* Stone duality"; `Topology/Order/Priestley.lean` defines only the `PriestleySpace` mixin (`lean_local_search` returns exactly one declaration); `Order/Category/BoolAlg.lean` is the bare category; `Topology/Category/Stonean/` is extremally-disconnected spaces, unrelated; `Topology/Order/Category/FrameAdjunction.lean` is the frames/locales adjunction. `Order/PrimeSeparator.lean:14-16` (Sam van Gool, 2024) states its purpose as "a crucial ingredient to Stone's duality for bounded distributive lattices". The ForMathlib layer of Phase 5 is therefore the natural next brick in an upstream direction that a Mathlib author has already begun — which raises, not lowers, the value of keeping Appendix A PR-shaped.

### 7. Verdict

**Is another `--lit` research round on task 528 worth running?** **No, not as a gate on the plan, and not with the corpus as it stands.** The three open decisions and the acceptance-criterion restatement are decided by Mathlib source (pinned locally and already read line-by-line by both reports), Mathlib convention documents (living pages, best consulted live at PR time), and downstream-project layout precedent (verified this round: `PFR/ForMathlib/`, `LeanLTL/ForMathlib.lean`). No book in the corpus, and none on the shortlist, would change D-A, D-B, or D-C; a fresh `--lit` round would re-derive report 02 with textbook citations attached.

**Plan v2 is sound as written on D-A and D-C.** On D-B the name `Order.PrimeFilter` is right and is corroborated by the owned CZ §8.2 text and by Davey-Priestley/Gehrke-van Gool vocabulary; the only refinement worth recording is Finding 2.3's `abbrev`-subtype vs `structure` trade-off against the `SetLike` template, which is a one-line addition to the D-B rationale, not a reversal.
